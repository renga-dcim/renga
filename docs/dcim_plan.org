#+title: Renga DCIM Plan

* Goal

Build Renga into a DCIM system that keeps a live, queryable inventory of physical hosts, network switches, virtual machines, and related resources by syncing from deployed agents and infrastructure integrations.

The system should answer:

- What resources exist right now?
- Where are they located?
- What changed recently?
- Which source reported each fact?
- Which records are stale, missing, duplicated, or conflicting?

* Product Principles

- Inventory is observed first, manually corrected second.
- Every fact has provenance: source, observed time, confidence, and raw evidence when useful.
- Syncs are idempotent and safe to retry.
- The central app reconciles state; agents only report observations.
- Stale data is visible instead of silently trusted.
- The first UI should be operational, dense, and searchable, not a marketing surface.
- Basic inventory sync must keep working even when the future control channel is unavailable.
- Powerful agent features must be gated by explicit capabilities, policy, and audit logs.

* Current Direction

- Start with host agents.
- Write the agent in Rust.
- Keep the Rust agent in this repository under =agent/= while the protocol and product shape are still evolving.
- Target Debian/Ubuntu first for agent packaging, with systemd service units and =.deb= packages.
- Target libvirt/KVM first for virtualization support, with cloud-hypervisor support following soon after.
- Use a protocol-first switch strategy: SNMP/LLDP for broad compatibility and gNMI/OpenConfig as a first-class modern collector path.
- Use HTTP POST for periodic inventory observations.
- Add a persistent control channel later for live terminal, pushed jobs, scheduling, and streaming command/query results.
- Use persisted jobs with polling as the required control-plane path and Phoenix Channels as the low-latency acceleration path.
- Keep switch polling and VM provider syncers in the architecture as future source types.
- Build SaaS-ready organization-scoped multi-tenancy from day one.
- Represent operator intent as desired resource state and use explicit field-level overrides only for manual corrections to observed inventory.
- Use Renga-native typed operational queries in the agent, and treat osquery as a separate optional endpoint integration for broad host inspection.
- Model Renga as both a live inventory system and, eventually, an automation control plane.
- Borrow NetBox's domain discipline for DCIM, IPAM, virtualization, tenancy, interfaces, tags, custom fields, and change logging.
- Diverge from NetBox by making agents, observations, reconciliation, freshness, jobs, capabilities, and desired-vs-observed state first-class.
- Store application timestamps at millisecond precision. Immutable observation rows should derive =inserted_at= from the millisecond timestamp encoded in their UUIDv7 primary key.

* System Shape

Renga is the central Phoenix application. It owns identity, inventory records, reconciliation, audit history, and the web UI.

External collectors report observations:

- Host agents installed on bare-metal servers or VM guests.
- Network collectors that poll switches through SNMP, LLDP, CDP, RESTCONF, NETCONF, or vendor APIs.
- Virtualization/cloud syncers for platforms such as Proxmox, vSphere, libvirt, Kubernetes, or cloud APIs.
- Optional out-of-band hardware syncers for Redfish/IPMI/BMC data.

Initial implementation should keep collectors simple and push observations to the Phoenix API over HTTPS. Long-running polling, reconciliation, and stale detection should live centrally.

The agent transport should be hybrid:

- HTTP POST for durable inventory observations.
- HTTP GET/POST for check-ins and config.
- WebSocket or Phoenix Channels later for pushed jobs, live query sessions, terminal sessions, scheduling coordination, and streaming output.

The observation payload and reconciliation pipeline should be transport-independent. A host agent, switch poller, VM provider syncer, or future WebSocket-connected agent should all emit the same internal concept: an observation from a source at a point in time.

* Core Domains

** Inventory

Canonical resources:

- Sites, rooms, rows, racks, rack positions.
- Devices: servers, switches, appliances, chassis, PDUs.
- Compute instances: VMs, containers, Kubernetes nodes, hypervisor guests.
- Network interfaces, MAC addresses, IP addresses, VLANs, links, and switch ports.
- Storage devices, disks, volumes, filesystems.
- Hardware components: CPUs, memory modules, NICs, PSUs, fans, GPUs, firmware.

NetBox-inspired domain boundaries to preserve:

- DCIM: sites, locations, racks, devices, modules, inventory items, cables, power.
- IPAM: prefixes, IP ranges, IP addresses, VLANs, VRFs.
- Virtualization: clusters, hypervisors, VMs, virtual interfaces, virtual disks.
- Tenancy: customer, team, project, business unit, or environment ownership.
- Extensibility: tags, custom fields, webhooks, exports, event rules, object permissions.

** Observability Of Inventory

Operational metadata:

- Source identity.
- Agent identity and lease health when a source is backed by a deployed agent.
- Last seen timestamp.
- Last successful inventory timestamp.
- First seen timestamp.
- Last changed timestamp.
- Sync run ID.
- Confidence level.
- Raw observation payload, retained with size limits.
- Field-level conflicts.
- Independent resource conditions for freshness, reachability, readiness, and reconciliation.

** Change History

Track resource changes as events:

- Resource discovered.
- Resource updated.
- Resource disappeared or became stale.
- Manual override added or removed.
- Source conflict detected.
- Agent registered, rotated, disabled, or deleted.

* Data Model Draft

Use PostgreSQL as the authoritative store. Keep identity, relationships,
allocations, conditions, ownership, and frequently queried projections in
relational tables. Use JSONB for variable desired state, detailed source
observations, and vendor-specific data. Do not add a KV store until measured
ephemeral load, connection routing, rate limiting, or cache pressure justifies
one.

The model has four distinct layers:

1. Resource envelopes identify independently addressable and reconcilable objects.
2. Typed canonical projections provide constrained, queryable current inventory.
3. Per-source evidence preserves provenance and disagreement.
4. Immutable observations preserve the raw submitted evidence.

Core tenant boundary:

- The MVP should use a single database with organization-scoped multi-tenancy.
- User-facing inventory, sources, observations, jobs, sites, racks, interfaces, IPAM records, and change events should carry =organization_id=.
- Agent tokens should be scoped to one organization.
- Jobs and control-plane sessions should be scoped to one organization.
- Unique constraints for user inventory should usually be organization-scoped.
- All user-facing queries should be scoped by the current organization.
- Phoenix LiveViews should carry current organization scope the same way authenticated user scope is carried.

Defer advanced tenancy features:

- Billing.
- Tenant-specific branding.
- Cross-organization sharing.
- Enterprise SSO.
- Per-tenant encryption keys.
- Database-per-tenant architecture.
- Region and data residency controls.

** Resource Envelope And Typed Projections

A =Resource= is the common envelope for an object that needs stable identity,
desired state, independent conditions, revisions, relationships, or lifecycle
management. Do not turn every fact into a resource. Addresses, conditions,
identifier claims, leases, and reconciliation results remain subordinate typed
records.

Recommended resource envelope fields:

- =organization_id=
- =kind=: =server=, =switch=, =vm=, =container=, =pdu=, =storage=, =unknown=
- =name= or =display_name=, which is not identity
- =lifecycle_state=: =active=, =inactive=, =retired=, =unknown=
- =spec=: JSONB desired state owned by users and controllers
- =generation=: incremented only when desired state changes
- =resource_version=: monotonically ordered revision for optimistic concurrency and future watches
- =labels=: low-cardinality selector metadata
- =annotations=: non-selector metadata
- =deletion_requested_at=: nullable lifecycle marker for future managed deletion
- millisecond-precision timestamps

Stable, frequently queried inventory remains in typed projections. Examples
include machine identity/display fields, interfaces, addresses, prefixes, rack
placement, and scheduling capacity. PostgreSQL =macaddr=, =inet=, =cidr=,
numeric, range, and timestamp types should be preferred over string or JSONB
representations when the domain has a native type.

Variable hardware details, full CPU flags, firmware extensions, and vendor data
may remain JSONB. Promote values into typed projections when they become search,
policy, allocation, or scheduling inputs.

The single lifecycle state is not a health summary. =ResourceCondition= records
represent independent facts such as =InventoryCurrent=, =AgentConnected=,
=Ready=, =Degraded=, and =Reconciling=. Conditions should include status,
reason, message, last transition time, the responsible manager, and an optional
observed generation.

** Desired State, Observed State, And Overrides

- Desired state is what users or controllers want and belongs in =Resource.spec= or typed desired-state tables.
- Observed evidence is what sources report and must never overwrite desired state directly.
- Canonical projections are server-owned results derived from current source evidence using deterministic precedence rules.
- Conditions explain whether desired and observed state have converged.
- Field-level overrides are reserved for explicit manual corrections to observed inventory, not rack placement, ownership, lifecycle intent, or other normal desired state.

When desired state changes, increment =generation=. Controllers record the
generation they evaluated so the UI can distinguish unprocessed intent from a
processed request that has not converged.

** Resource Identity And Claims

Resource identity must not depend on one field. Separate canonical identifiers
from source claims:

- =ResourceIdentifier= associates a normalized identifier with a canonical resource.
- =ResourceIdentifierClaim= records which source and observation asserted that identifier, with confidence and first/last seen timestamps.

Identifier kinds include hostname, FQDN, machine ID, DMI UUID, serial number,
MAC address, provider instance ID, and BMC address. Kind-specific normalization
must happen before matching.

Do not enforce organization-wide uniqueness for source-reported serial numbers
or provider external IDs. Renga must be able to represent duplicate and
conflicting claims before reconciliation decides what they mean. Human-managed
asset tags may remain organization-unique when policy requires it.

This split lets multiple sources confirm the same identifier and lets the system
retain disagreement without corrupting canonical identity.

** Sources, Agents, And Leases

A =Source= is an authenticated reporting authority and provenance anchor. An
=Agent= is a registered runtime installation that may use a source credential.
Do not use one row to represent both concepts.

Recommended source fields:

- =kind=: =host_agent=, =switch_poller=, =vm_provider=, =bmc=, =manual=
- =name=
- credential and revocation state
- expected observation interval and freshness policy
- metadata

Recommended agent fields:

- =source_id=
- stable installation ID
- optional managed resource ID
- version and capabilities
- registration and configuration metadata

=AgentLease= stores holder/session identity, renewal time, and lease duration.
Lease renewal is lightweight and independent from full inventory collection.
Keep separate timestamps for API contact, latest inventory, latest successful
inventory, and lease renewal. Agent online and inventory current are different
conditions.

** Immutable Observations And Processing

=Observation= is immutable raw evidence. It contains the organization, source,
optional sync run, source-provided idempotency key, observed time, payload
digest, payload, metadata, UUIDv7 ID, and matching =inserted_at=. It does not
contain mutable processing status, reconciliation errors, or a canonical
resource assignment.

=ObservationReconciliation= records processing attempts, result status,
candidate or matched resources, errors, and completion timestamps. Retrying
reconciliation creates or updates processing state without mutating raw
evidence.

Require a source-scoped observation idempotency key. Use the payload digest to
detect conflicting reuse of that key, not as permanent uniqueness for all
reports. An unchanged host must be able to submit the same inventory again at a
later observed time.

** Canonical Network State And Provenance

Interfaces, addresses, and typed topology rows are source-neutral canonical
records. Per-source evidence records link them to sources and observations so
host agents, hypervisors, BMC collectors, and switch collectors can agree or
conflict without one source replacing another's provenance.

Interface MAC addresses use PostgreSQL =macaddr=. Assigned or observed interface
addresses use =inet=. Managed IPAM prefixes use =cidr=. Directed typed interface
relationships capture bond membership, bridge membership, lower-device
stacking, veth peers, VRF membership, and virtual interface backing links.

Use generalized =ResourceRelationship= records only for cross-domain topology
that does not belong in a stronger typed table. Keep lifecycle ownership in
=ResourceOwner= rather than treating every relationship as ownership. Add
finalizers only when destructive management and cleanup workflows exist.

** Reconciliation And Audit, Not Full Event Sourcing

This model is similar to event sourcing, but Renga should not start as a fully event-sourced system.

Full event sourcing would make the ordered event stream the authoritative source of state, with resource tables rebuilt as projections. That can be powerful, but it adds complexity around event schema versioning, replay logic, projection rebuilds, ordering, ad hoc repair, and testing.

Start with a simpler model:

- =resources=: identity, desired state, lifecycle, and revision envelope.
- typed inventory tables: canonical current query projections.
- per-source evidence and identifier claims: current provenance and conflicts.
- =observations=: immutable raw reported payloads.
- =observation_reconciliations=: processing attempts and outcomes.
- =change_events=: audit/history of meaningful changes.

The write path should be:

1. Store the raw observation.
2. Record or refresh per-source evidence and identifier claims.
3. Reconcile evidence into canonical resources, conditions, interfaces, addresses, and related typed projections.
4. Write change events for meaningful discoveries, updates, conflicts, stale transitions, and manual edits.

This gives Renga provenance, conflict detection, stale detection, debugging history, and a possible replay path later without making every normal read depend on event replay.

Observation rows should be immutable append-only records. Their primary keys
should be UUIDv7 so row identity carries useful creation-time ordering. Keep
=observed_at= for the source-reported event time and =inserted_at= for storage
time; do not add =updated_at= to observations.

Manual edits should be field-level override records, not silent mutation of observed facts.

Suggested override fields:

- =organization_id=
- =resource_id=
- =field=
- =value=
- =reason=
- =created_by_user_id=
- =inserted_at=

Override rules:

- Manual override wins in canonical display.
- Observations are still stored.
- Conflicts between observed and overridden values remain visible.
- Overrides are field-scoped, auditable, and removable.
- Desired fields such as rack position, owner, lifecycle intent, and notes belong in =spec= or typed desired-state records instead of overrides.

* Agent And Collector Model

** Host Agent

The host agent reports:

- Hostname and FQDN.
- Machine ID, DMI UUID, serial number, vendor, model.
- CPU, memory, disks, filesystems, NICs.
- IP and MAC addresses.
- OS name, version, kernel.
- Virtualization hints: bare metal, VM guest, container host.
- Optional BMC address if discoverable.

The agent should not decide whether it is a duplicate of another record. It sends stable identifiers and lets Renga reconcile.

The host agent should be implemented in Rust and structured around modules:

- =agent-core=: identity, config, auth, scheduler, transports, local observation queue.
- =collectors=: host facts, network interfaces, disks, filesystems, packages, processes, virtualization hints.
- =control=: job runner, leases, result reporting, streaming output.
- =query=: safe Renga-native operational queries over predefined typed tables.
- =virtualization=: libvirt/KVM first, cloud-hypervisor soon after, and related local hypervisor integrations.

The first Rust agent should be intentionally boring:

- Runs as a daemon/service from the beginning.
- Uses an internal scheduler for periodic inventory collection, check-ins, and config refresh.
- Ships with a systemd unit for Linux proof of concept deployments.
- Supports =--once= only as a development and troubleshooting mode.
- Supports =--dry-run= to print the JSON observation.
- Collects host facts.
- Posts the observation.
- Does not support remote shell or VM placement yet.

Agents should advertise capabilities, for example:

#+begin_src json
{
  "capabilities": [
    "host.inventory",
    "host.query",
    "vm.libvirt.read",
    "vm.libvirt.manage"
  ]
}
#+end_src

Agent roles should be explicit:

- =observer=: can report inventory.
- =query_runner=: can answer approved live queries.
- =executor=: can perform controlled jobs.
- =hypervisor=: can manage local VMs.
- =terminal=: can open interactive terminal sessions.

** Switch Collector

The switch collector reports:

- Device identity, model, OS, serial number.
- Interfaces and admin/oper state.
- MAC address tables.
- LLDP/CDP neighbors.
- VLAN membership.
- Port descriptions.

This can initially run as a central collector instead of software deployed to switches.

Switch support should be protocol-first:

- Baseline compatibility path: SNMP plus LLDP read-only polling.
- Modern path: gNMI/OpenConfig read-only collection.
- Initial data: switch identity, interfaces, interface state, and LLDP neighbors.
- Later data: MAC address tables, VLAN details, streaming telemetry, and vendor-specific extensions.

If a target fleet supports gNMI/OpenConfig cleanly, prioritize that path. Keep SNMP/LLDP as the compatibility baseline for older or mixed environments.

** VM Provider Sync

Provider syncers report:

- VM identity and lifecycle state.
- Hypervisor or cluster placement.
- vCPU, memory, disks, NICs.
- Guest hostname and tools status when available.
- Relationship to host resource.

* Ingestion API

Initial endpoints:

- =POST /api/v1/agent/register=
- =POST /api/v1/observations=
- =POST /api/v1/sync_runs/:id/complete=
- =GET /api/v1/agent/config=
- =POST /api/v1/agent/checkins=

Observation payload shape:

#+begin_src json
{
  "source": {
    "kind": "host_agent",
    "source_id": "host-agent-01"
  },
  "observed_at": "2026-07-29T12:00:00Z",
  "resources": [
    {
      "kind": "server",
      "identifiers": {
        "hostname": "compute-01",
        "serial_number": "ABC123",
        "machine_id": "..."
      },
      "attributes": {
        "vendor": "Dell Inc.",
        "model": "PowerEdge R760"
      },
      "interfaces": [],
      "components": []
    }
  ]

API requirements:

- Authenticate each source with a bearer token.
- Store every accepted observation.
- Require a source-provided observation idempotency key.
- Use the payload digest to reject conflicting reuse of an idempotency key while allowing identical inventory to be reported again under a new key.
- Return per-resource acceptance and validation errors.
- Avoid accepting client-controlled canonical IDs.

* Control Plane

Control-plane features should be layered on after basic inventory sync works. The durable abstraction should be a persisted job, not the WebSocket itself.

Suggested job fields:

- =kind=: =collect_inventory=, =run_query=, =vm_create=, =vm_start=, =vm_stop=, =terminal_session=.
- =status=: =queued=, =leased=, =running=, =succeeded=, =failed=, =expired=, =cancelled=.
- =target_agent_id= or =target_resource_id=
- =requested_by=
- =params=
- =result=
- =error=
- =expires_at=
- =inserted_at=
- =started_at=
- =completed_at=

Job rules:

- Jobs are persisted before delivery.
- Agents lease jobs before running them.
- Jobs expire if not leased or completed in time.
- Agents reject jobs outside their advertised and locally enabled capabilities.
- Every state transition becomes a job event.
- Polling job lease endpoints are the required transport.
- Phoenix Channels/WebSocket delivery is an acceleration path for connected agents.
- Jobs must survive disconnects and restarts.
- Agents fall back to polling when the socket is disconnected.
- Inventory observations continue to use HTTP POST.

Future control endpoints:

- =GET /api/v1/agent/jobs=
- =POST /api/v1/agent/jobs/:id/lease=
- =POST /api/v1/agent/jobs/:id/events=
- =POST /api/v1/agent/jobs/:id/complete=
- =GET /api/v1/agent/socket_config=
- =WebSocket /agent/socket=

** Live Terminal

Live terminal is useful but high risk. It should not be enabled by default.

Prerequisites before implementation:

- Strong user authentication and RBAC.
- Agent-side allow/deny configuration.
- Per-session leases with short expiration.
- Full audit trail.
- Session recording or command logging.
- Clear policy for which users can reach which sources.

** Live Queries

The Renga agent should support native typed operational queries, not try to become a full osquery replacement.

Renga-native query examples:

- =interfaces=
- =addresses=
- =disks=
- =mounts=
- =hardware_summary=
- =agent_status=
- =vms=
- =libvirt_domains=
- =cloud_hypervisor_vms=
- =capacity=

These queries should be read-only, collector-backed, typed, and directly useful for DCIM, hypervisor state, capacity planning, and automation decisions. They should map cleanly into Renga resources, jobs, and observations.

Do not allow arbitrary shell execution through the query interface.

Potential Renga-native capability names:

- =host.query.basic=
- =host.query.inventory=
- =host.query.capacity=
- =vm.query.libvirt=
- =vm.query.cloud_hypervisor=

*** Osquery Integration

Osquery should be treated as a separate optional integration for broad endpoint inspection, security, and compliance use cases.

The preferred later integration is to implement osquery-compatible remote HTTP endpoints in Renga so existing =osqueryd= deployments can enroll, fetch config, receive distributed queries, and post results.

Potential osquery endpoints:

- =POST /osquery/enroll=
- =POST /osquery/config=
- =POST /osquery/log=
- =POST /osquery/distributed/read=
- =POST /osquery/distributed/write=

Use osquery for broad endpoint tables such as:

- =processes=
- =packages=
- =users=
- =listening_ports=
- =kernel_modules=
- =file_events=
- security/compliance packs

The Renga agent remains the primary inventory, control, and automation agent. Osquery remains an optional companion for hosts where =osqueryd= is installed and configured.

** VM Placement

VM placement turns Renga from inventory into automation. Treat placement as desired state plus controlled jobs.

Placement needs:

- Host capacity model.
- Reserved vs used resources.
- Overcommit policy.
- Storage pool availability.
- Network attachment options.
- Maintenance/drain state.
- Anti-affinity and placement constraints eventually.
- Cleanup behavior if a create/start/migrate job fails.

Start with libvirt/KVM on a single host before generalizing to clusters. Add cloud-hypervisor support soon after the libvirt path proves the job, capability, and inventory model.

* Reconciliation Rules

Canonical resource matching should prefer stable hardware identifiers:

1. BMC or chassis serial number.
2. DMI product UUID plus source type.
3. Cloud or VM provider instance ID.
4. Switch serial number.
5. MAC address sets.
6. Hostname/FQDN as a weak signal only.

When sources disagree:

- Keep the canonical record stable.
- Record field-level conflict details.
- Prefer source types by configurable priority.
- Preserve every current source claim and its raw observation evidence.
- Keep desired state and manual corrections separate from observed facts.
- Update independent resource conditions instead of collapsing disagreement into one status enum.

* Freshness And Lifecycle

Suggested lifecycle:

- =active=: resource is in service.
- =inactive=: resource is intentionally not active.
- =retired=: resource is manually retired or removed by policy.
- =unknown=: lifecycle intent has not been established.

Freshness is a condition, not lifecycle. =InventoryCurrent= becomes false when
the current evidence exceeds its source policy. =AgentConnected= is derived
from the agent lease. A resource may be active while its inventory is stale or
its agent is disconnected.

Each source should define:

- Expected sync interval.
- Stale-after duration.
- Whether syncs are full snapshots or partial observations.

* Phoenix Implementation Slices

** Slice 1: Inventory Foundation

- Add =Renga.Inventory= context.
- Add resource envelopes, typed projections, conditions, canonical identifiers, per-source claims, immutable observations, reconciliation results, agents, leases, interfaces, addresses, sync runs, and audit events.
- Store interface MAC addresses as PostgreSQL =macaddr=, interface IP addresses as PostgreSQL =inet=, and future IPAM prefixes/subnets as PostgreSQL =cidr=.
- Add basic CRUD functions in the context.
- Add tests for creation, source evidence, safe duplicate representation, observation immutability, conditions, leases, and lifecycle transitions.

** Slice 2: Ingestion API

- Add JSON API routes under =/api=.
- Add source token authentication plug.
- Accept host-agent observation payloads.
- Store raw observations.
- Store processing outcomes outside immutable observations.
- Add tests for auth, source-scoped idempotency, conflicting key reuse, validation, and repeated identical reports.

** Slice 3: Reconciliation MVP

- Normalize and preserve per-source identity claims.
- Match canonical resources using strong identifiers before weak names.
- Reconcile source evidence into source-neutral typed projections.
- Apply deterministic field ownership and precedence rules.
- Update resource conditions and write non-authoritative audit events.
- Add tests for duplicate identifiers, multi-source agreement, conflicts, and stale evidence.

** Slice 4: Rust Host Agent MVP

- Create a Rust agent workspace under a dedicated top-level =agent/= directory.
- Implement daemon lifecycle, config loading, identity, auth, internal scheduling, host inventory collection, dry-run output, check-ins, and POST transport.
- Add systemd unit files for development/proof-of-concept deployment.
- Package Debian/Ubuntu first with =.deb= artifacts.
- Provide a raw static binary or tarball artifact for development and non-Debian testing.
- Leave remote command execution, terminal sessions, and VM placement out of the first agent cut.

** Slice 5: Operational UI

- Replace the generated home page with a LiveView inventory dashboard.
- Add resource list, resource detail, source list, stale-resource filters, and recent change events.
- Use LiveView streams for lists that update.
- Add key DOM IDs for tests.

** Slice 6: Durable Jobs And Agent Capabilities

- Add persisted jobs and job events.
- Add source capabilities.
- Add polling-based job lease endpoints.
- Add safe read-only live query jobs.
- Add audit events for job lifecycle changes.

** Slice 7: Phoenix Channels Control Acceleration

- Add Phoenix Channel or socket endpoint for connected agents.
- Use it to notify agents about queued jobs and stream job output.
- Keep polling endpoints as the required fallback and correctness path.

** Slice 8: Switch And VM Syncers

- Add a central collector process for switch polling.
- Add provider-specific sync behavior behind a common behaviour module.
- Start VM sync with libvirt/KVM read-only inventory.
- Add cloud-hypervisor support soon after libvirt/KVM.
- Start switch sync with SNMP/LLDP and gNMI/OpenConfig read-only collection.

* Security

- Agent tokens must be generated centrally and stored hashed.
- Tokens should be scoped to one source.
- Tokens should be rotatable and revocable.
- Avoid shared fleet-wide tokens.
- TLS is mandatory outside local development.
- Observation payloads should have size limits.
- Raw payload retention should be capped by age and count.
- Manual edits should be audited.
- API should reject unknown source kinds unless explicitly enabled.
- Capabilities should be enforced on both the server and the agent.
- Live terminal and executor capabilities should require explicit opt-in.

* Testing Strategy

- Context tests for resource matching and lifecycle transitions.
- Controller tests for API auth and validation.
- LiveView tests for key dashboard and detail selectors.
- Fixture payloads for host, switch, and VM observations.
- Reconciliation tests that cover duplicate and conflicting identifiers.

* Recommended MVP

Build the host-agent path first:

1. Manual source creation with generated token.
2. Agent registration and renewable lease separate from source authentication.
3. =POST /api/v1/observations= with source-scoped idempotency keys.
4. Immutable raw observations and separate reconciliation outcomes.
5. Canonical server and interface projections backed by per-source evidence.
6. Canonical identifiers plus source claims for machine ID, DMI UUID, serial number, hostnames, and MAC addresses.
7. Inventory freshness and agent connectivity represented as independent conditions.
8. Rust service agent with internal scheduling, leases, check-ins, =--once=, =--dry-run=, config, auth, and POST transport.
9. Inventory dashboard showing lifecycle and freshness separately.
10. Resource detail view showing desired state, canonical projections, observed facts, provenance, conditions, identifiers, and last sync.

This creates the smallest useful loop: deploy an agent, report a host, update inventory, and see freshness in the UI.

* NetBox Ideas To Adopt

Adopt:

- Clear domain separation across DCIM, IPAM, virtualization, and tenancy.
- Interfaces as first-class records.
- IP addresses assigned to interfaces.
- Prefixes, VLANs, and VRFs as real IPAM records.
- Manufacturer, platform, and hardware type concepts.
- Tags and custom fields.
- Change logging.
- Webhooks or event rules later.
- Tenant assignment later, even if not day one.

Do not copy blindly:

- NetBox is primarily a system of record. Renga should be live observed inventory plus automation.
- Renga needs source provenance, raw observations, reconciliation, freshness, job leases, agent capabilities, and control-plane audit trails as core concepts.
- Renga should not require manual modeling before it can discover useful facts from hosts.
