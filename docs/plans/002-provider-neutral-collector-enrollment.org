#+title: Organization Intake Keys And Automatic Collector Registration
#+status: Active

* Objective

Make host-agent installation simple enough for the product's current stage:

1. An organization owner or administrator creates an intake API key.
2. The same key may be deployed to every agent in that organization.
3. Each agent generates and persists its own installation UUID on first boot.
4. Renga automatically creates the existing =Source(kind: "host_agent")= and
   =Agent= records when that installation first checks in.
5. Observations remain attributable to the installation's Source even though
   the API key authenticates the organization rather than an individual agent.

Use a Datadog-style intake trust model as the default. Do not require an
enrollment protocol, OIDC, keypairs, proof of possession, short-lived runtime
credentials, or admission policy before the inventory service has demonstrated
a need for them.

* Scope

** In Scope

- Organization-level intake API keys stored as hashes and revealed once.
- Multiple simultaneously active keys so fleets can rotate without downtime.
- Owner/admin key creation and revocation in the existing authenticated,
  organization-selected operations UI.
- Shared-key authentication for agent check-ins and observations.
- Automatic Source+Agent registration from an organization-scoped installation
  UUID.
- Agent generation and durable storage of its installation UUID on first boot.
- Preservation of per-installation provenance, lease health, and inventory
  freshness.
- A direct migration from current per-Source credentials, or a temporary
  compatibility window if deployed agents require one.

** Out Of Scope

- OIDC, workload identity federation, SPIFFE, cloud identity, or TPM
  attestation.
- Enrollment challenges, grants, attempts, approvals, or proof of key
  possession.
- ABAC or enrollment-policy evaluation.
- Per-agent API keys.
- Deployment-group API keys or key scopes.
- API-key expiration or automatic credential renewal.
- Using the intake key for terminal sessions, command execution, desired-state
  mutation, organization reads, or collector administration.

Group-scoped and per-agent credentials may be added later when requested by
real deployments. They are optional reductions in credential blast radius, not
requirements for the initial intake model.

* Design Decisions

** Authentication And Identity

An intake API key authenticates one active organization. It does not
cryptographically authenticate an individual installation. The agent's
=x-renga-installation-id= identifies the reporting installation within that
organization and is accepted as a correlation identifier under the shared-key
trust model.

Anyone possessing an organization's intake key can submit inventory for that
organization and can impersonate an installation whose UUID they know. This is
an explicit simplicity tradeoff. Require HTTPS, restrict intake keys to agent
intake endpoints, store only hashes, redact keys from logs and diagnostics, and
allow independent key revocation.

The intake key may authorize only:

- =POST /api/v1/agent/checkins=
- =POST /api/v1/observations=

Future privileged control-plane operations must use a separate authorization
design rather than expanding the intake key's authority.

** Credential Model

Add an organization-scoped =IntakeApiKey= model with the minimum fields needed
for issuance, authentication, rotation, and revocation:

- =organization_id=
- =name=
- =token_hash=
- =status=: =active= or =revoked=
- timestamps

Token hashes must be unique. Plaintext keys are returned only at creation and
cannot be reconstructed. An organization may have multiple active keys so an
operator can create a replacement, deploy it, and revoke the old key after the
fleet switches.

Do not add scopes, deployment groups, expiry, usage counts, policy selectors,
or per-agent ownership until a concrete requirement needs them.

** Source, Agent, And Provenance

Keep =Source= as the producer and provenance anchor for observations, evidence,
and reconciliation. Keep =Agent= as the runtime installation record and
=AgentLease= as its independent connection-liveness record.

For host agents, one automatically registered installation receives one Source
and one Agent:

- the intake key authenticates the organization;
- the installation UUID resolves the Agent within that organization;
- the Agent points to its per-installation Source;
- observations and derived evidence continue to point to that Source.

This preserves per-installation provenance without issuing per-installation
credentials. Source names must be generated from a stable server-controlled
scheme using the installation UUID, not from self-reported hostname alone.

First check-in and first observation must converge safely when concurrent. The
registration transaction revalidates the active organization and intake key,
finds or creates the installation's Source+Agent records, renews its lease, and,
for observation ingestion, stores the observation against the resolved Source.

Keep organization-scoped uniqueness for =Agent.installation_id=. Remove the
one-Agent-per-Source assumption only if implementation requires it; automatic
registration should still create one dedicated Source for each Agent.

** Agent State

The agent generates a UUID on first startup and persists it in a strictly
permissioned state directory, expected to be under =/var/lib/renga=. It reuses
that UUID across service restarts and package upgrades.

Normal configuration contains only the Renga URL, intake API key, intervals,
and existing collection settings. An explicitly configured installation UUID
may remain temporarily for compatibility, but is not part of the default setup.

Golden images and templates may share an organization intake key as an explicit
property of this trust model. They must not contain a pre-generated installation
UUID or copied agent state; every clone generates a distinct UUID on first boot.

** Rotation And Revocation

Rotation uses overlapping organization keys rather than an in-place replacement:

1. Create and reveal a new intake key.
2. Deploy it to the fleet.
3. Confirm the old key is no longer needed using available operational evidence.
4. Revoke the old key.

Revoking a key affects every agent still using it. It does not delete Sources,
Agents, observations, or provenance. Disabling an Agent remains an operational
lifecycle action; with a shared organization key, it is not an authentication
barrier against a caller that deliberately reuses that installation UUID.

* Deprecated MVP Behavior

Deprecate the following behavior introduced by the host-agent MVP:

- =Source.token_hash= as the default credential store.
- One credential created for each manually created host-agent Source.
- =create_source_with_token/2= and collector-specific token issuance.
- Per-Source token rotation and revocation for host agents.
- Manual creation of an installation UUID in the collector UI.
- The requirement to configure =installation_id= in =agent.toml=.
- Exclusive binding of a Source credential to one installation.
- Collector enrollment reset, where deleting the Agent lets another
  installation claim that Source credential.
- "Enrollment token" terminology for ordinary agent intake.

Do not deprecate =Source=, =Agent=, =AgentLease=, =Observation=, =SyncRun=, or
the source-linked evidence models. Their provenance and operational roles remain
valid under organization-level authentication.

* Migration

If there are no deployed agents or production data requiring compatibility,
update the development migrations and reset development/test databases rather
than preserving the superseded Source-token model.

If deployed agents require a compatibility window:

1. Add organization intake keys and make them the default setup path.
2. Temporarily authenticate either an organization intake key or a legacy
   Source token.
3. When an existing installation switches to an organization key, resolve its
   existing Agent and Source by organization and installation UUID so history
   remains attached.
4. Expose enough usage information to identify remaining legacy authentication.
5. Remove legacy Source-token authentication and =sources.token_hash= after its
   use reaches zero.

Because only Source token hashes are stored, existing plaintext credentials
cannot be converted into organization intake keys. A new organization key must
be generated and deployed.

* Acceptance Criteria

- [ ] An owner/admin can create an organization intake key, see it once, and
  revoke it without deleting inventory or provenance.
- [ ] Multiple organization intake keys can remain active during fleet rotation.
- [ ] The same intake key can authenticate check-ins and observations from many
  installation UUIDs in one organization.
- [ ] First contact from each new installation creates exactly one dedicated
  Source+Agent aggregate, including under concurrent requests.
- [ ] Each observation is attributed to the Source associated with the reporting
  installation UUID.
- [ ] The agent generates and persists its installation UUID without requiring
  an operator to configure one.
- [ ] Restart and package upgrade preserve installation identity, while cloned
  images without persisted state generate distinct identities.
- [ ] An intake key cannot access browser, administration, organization-read, or
  future privileged control-plane endpoints.
- [ ] Revoked keys and keys belonging to disabled organizations are rejected.
- [ ] Existing deployed agents either migrate without losing Source provenance
  or the project explicitly uses a clean development reset.
- [ ] No OIDC, verifier, challenge, ABAC, keypair, runtime-credential renewal,
  group-key, or per-agent-key model is introduced by this plan.
