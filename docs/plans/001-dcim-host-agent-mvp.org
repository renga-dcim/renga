#+title: DCIM Host Agent MVP
#+status: Draft

* Objective

Build the smallest useful Renga DCIM loop:

1. Create an organization-scoped source for a host agent.
2. Run a Rust service agent on a Debian/Ubuntu host.
3. Collect host inventory facts.
4. POST observations to Renga.
5. Reconcile observations into canonical inventory.
6. Show active/stale resources and their provenance in the UI.

This MVP proves the core product model before adding switch polling, VM lifecycle automation, live terminal sessions, osquery-compatible endpoints, or placement decisions.

* Scope

** In Scope

- Organization-scoped multi-tenancy.
- Inventory foundation for host-agent observations.
- Explicit resource identity records separate from resource fields.
- Raw observation storage.
- Source registration and token-based source authentication.
- Rust agent daemon under =agent/=.
- Debian/Ubuntu packaging path with systemd.
- HTTP POST observation ingestion.
- Check-ins and freshness/staleness tracking.
- Basic operational LiveView UI.
- Field-level manual override data model, even if the first UI for overrides is minimal.

** Out Of Scope

- Live terminal sessions.
- VM creation, start, stop, migration, or placement.
- Phoenix Channels control acceleration.
- Switch collectors.
- gNMI/OpenConfig, SNMP, and LLDP implementation.
- Cloud-hypervisor support.
- Osquery-compatible endpoints.
- Billing, SSO, per-tenant databases, and advanced SaaS tenancy features.

* Design Decisions

- Agent lives in this repository under =agent/=.
- Agent is Rust and daemon-first.
- Normal inventory transport is HTTP POST.
- =--once= and =--dry-run= exist for development, troubleshooting, smoke tests, and packaging validation.
- Persisted jobs and Phoenix Channels are planned later; they are not needed for the first inventory loop.
- Tenant boundary is =organization_id= in a single database.
- Agent tokens are scoped to one organization and one source.
- Resource identity is modeled as observed identifier facts.
- Resource fields are the canonical current view.
- Manual edits are explicit field-level overrides that preserve observed facts.

** 2. Inventory Data Model

- [X] Add =Resource= schema with organization scope, kind, canonical fields, status, metadata, and freshness timestamps.
- [X] Add =ResourceIdentifier= schema for observed identity facts.
- [X] Add =Interface= and =Address= schemas for first-class network inventory, storing MAC addresses as PostgreSQL =macaddr= and interface IP assignments as PostgreSQL =inet= values.
- [X] Add =InterfaceRelationship= schema for directed bond, bridge, peer, lower-device, VRF, and virtual backing relationships.
- [X] Add =Observation= and =SyncRun= schemas for raw payload storage and ingestion tracking.
- [X] Add =ChangeEvent= schema for resource discoveries, updates, conflicts, stale transitions, and manual edits.
- [X] Add =ResourceOverride= schema for field-level manual overrides.
- [X] Add uniqueness constraints scoped by =organization_id= where appropriate.
- [X] Add context tests for identifiers, resource creation, overrides, and freshness transitions.

IPAM prefixes/subnets should be modeled separately from observed interface
addresses when IPAM lands. Use PostgreSQL =cidr= for managed prefix records,
PostgreSQL =inet= for assigned or observed interface IP addresses, and
PostgreSQL =macaddr= for first-class interface MAC addresses.

Interface topology should use directed relationship rows instead of one generic
parent field. This keeps Linux host relationships such as bond members, bridge
members, veth peers, VLAN lower devices, and VRF membership compatible with
future libvirt and cloud-hypervisor virtual interface backing links.

Observation rows are immutable append-only records. Use UUIDv7 primary keys for
time-sortable row identity and keep =observed_at= plus =inserted_at= timestamps;
do not store an =updated_at= timestamp on observations. Store timestamps at
millisecond precision across all tables. Observation =inserted_at= values should
match the millisecond timestamp encoded in their UUIDv7 primary key.

* Acceptance Criteria

- [ ] A new organization can create or receive a host-agent source with a scoped token.
- [ ] A Rust service agent can run on Debian/Ubuntu under systemd.
- [ ] The agent can collect host facts and POST a valid observation.
- [ ] Renga stores the raw observation and reconciles it into canonical inventory.
- [ ] Resource identifiers are preserved separately from canonical fields.
- [ ] Repeated observations are idempotent.
- [ ] Stale resources are visible after their source misses the expected interval.
- [ ] The UI shows resources, sources, identifiers, interfaces, addresses, change events, and freshness.
- [ ] Tenant isolation tests prevent cross-organization access.
- [ ] =mix precommit= passes.
