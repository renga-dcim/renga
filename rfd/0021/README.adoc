= RFD 21 Per-organization limits

== Goal

Keep one organization from degrading Renga for the others in a deployment that
serves several. Today nothing stops one organization's agents, people, or
background work from taking the whole database:

* Every resource write in every organization takes one global advisory lock
  to allocate its revision (`Renga.Inventory.ResourceStore.next_revision!/0`).
  A burst of intake from one organization queues every other organization's
  writes behind it.
* Intake runs synchronously in the request transaction with no
  per-organization cap, so one organization's agents can hold most of the
  database connection pool.
* Background sweeps walk organizations one after another with no time budget,
  so one large organization delays the rest.
* The only per-organization limit is job creation, at 10,000 jobs a minute.

A deployment that serves one organization keeps today's behavior: the default
limits are generous, and the lock change helps it too.

== Removing global contention

=== Revision allocation

Revision allocation holds a lock until commit so that anyone reading changes
in revision order never skips a revision that is allocated but not yet
visible. Every such reader is scoped to one organization, so the order only
has to hold within an organization. The lock becomes per organization, keyed by
the organization ID in a resource-revision-specific advisory-lock namespace.
The revision sequence stays global, so revisions remain unique and increase
within each organization; they no longer say anything about order across
organizations, which nothing relies on.

Old writers taking only the global lock cannot run alongside writers taking
the new lock: they could commit revisions for one organization out of order.
The deployment that enables the new allocator therefore stops and drains all
resource writers, including background work, deploys the new allocator to
every node, and only then resumes writes. A future rolling cutover would need a
staged dual-lock protocol instead.

=== Other locks

Renga's other advisory locks are already keyed by organization, alone or
together with an installation, a source, or the hierarchy being changed. New
code follows the same rule: a lock that serializes work across organizations needs a reason in
its RFD.

== Request limits

Each organization gets rate limits. Intake admission has two bounded stages so
traffic cannot exhaust the database pool before Renga learns which organization
owns it. A small node-wide authentication lane bounds credential lookups for
valid and invalid callers. After lookup, but before any domain write, the
organization and installation limits apply. Latest authenticated contact still
includes rejected authenticated requests as RFD 1 requires, but contact writes
are coalesced by installation through a bounded recorder rather than issuing a
database update for every rejected request.

* *Intake*: observations, check-ins, job leases, and job events are limited per
  organization and per installation. Bulk observation traffic has its own
  capacity. Check-ins and reports for already-leased jobs have reserved
  capacity, and Renga stops granting new leases before that reserve is needed.
  This keeps lease maintenance available when observations are throttled.
  Exhausted capacity returns `429` with `Retry-After`.
* *Intake size*: the largest observation an organization may send.
* *Concurrency*: at most a set number of admitted intake operations per
  organization run at once on each node, a fraction of the connection pool by
  default. Admission is held through the complete synchronous operation,
  including observation acceptance and inline reconciliation even though they
  use separate transactions. Extra requests get `429` rather than waiting for
  a connection.
* *People and API*: HTTP requests, authenticated LiveView navigations, and
  LiveView events are limited per user and per organization, high enough that
  nobody working normally meets them. A throttled LiveView event does not run
  its handler and shows a retryable notice; an HTTP request gets `429`.

`Retry-After` is a retry-not-before deadline, not permission to exceed an
agent's delivery budget. If the deadline and another request cannot fit in the
current 25-second budget, the agent returns control and schedules a later
attempt instead of sleeping past the budget. It keeps observations and
terminal job outcomes durable until delivery. If overload nevertheless lets a
job lease expire, Renga applies RFD 9's existing retry-class transition and
records `lease_lost`; it never treats an unreported outcome as delivered.

Job creation keeps its existing limit, which becomes one of these settings.

== Database time

Every application database connection has a baseline `statement_timeout`, so
standalone reads and writes are covered as well as explicit transactions.
Requests use the shorter application default. Approved background workers may
set a longer transaction-local timeout for their own queries; work such as a
future export (RFD 20) runs there. Because `statement_timeout` bounds each
statement rather than a whole job, every worker also has a wall-clock budget
and a resumable boundary.

== Background work

Sweeps such as neighbor expiry and job history purge process each
organization in bounded batches and move on to the next organization when a
batch or its time budget is used, returning to unfinished organizations on the
next pass. One organization's failure is already logged and skipped; with
batches, one organization's size no longer delays the others either.

Future background work that runs per organization uses the same pattern, or a
queue that schedules organizations fairly, rather than draining one
organization before starting the next.

== Quotas

An organization has quotas on what it stores:

* resources;
* agents and installations;
* intake keys;
* terminal recording storage (RFD 13);
* export archives kept for download (RFD 20).

At 80% of a quota Renga opens a finding for the organization's owners. At the
quota, Renga refuses to create more of that thing and says which quota stopped
it. It never deletes data or stops updates to existing records. For resources
created by intake, Renga keeps the observation but defers creating the new
resource, and the finding lists what is waiting, so nothing an agent reported
is lost and it is reconciled once there is room.

== Configuration

Every limit and quota has a default, which an operator sets for the deployment
through the environment. An operator can override them for one organization
with a release command, such as `renga limits set --organization <slug>
--intake-rate 600`. Organization owners see their usage against each limit and
quota on a read-only page in organization settings; they cannot change them.

Renga emits telemetry for intake requests, intake bytes, database time, and
rejected requests, tagged with the organization ID, so an operator can see which
organization is using what before it reaches a limit.

An organization that needs more than a shared deployment can give it can move
to a deployment of its own with an export and import (RFD 20).

== Open questions

. *Default values.* The proposal leaves the defaults to the implementation,
  measured against realistic intake from a large organization.
. *Deferred resources.* Deferring resource creation at the quota keeps
  observations but leaves inventory incomplete. Accepting the resources and
  only warning would keep inventory complete but make the quota advisory.

== Future work

* Usage-based limits on stored history and raw observations.
* Limits on saved-view and query cost once RFD 12 queries exist.
