= RFD 19 Passkeys and multi-factor authentication

== Goal

Make Renga's own sign-in strong enough that people are not asked to sign in
again during normal work.

Today a Renga account signs in with a password or an emailed magic link, and
user settings demand a sign-in within the last ten minutes ("sudo mode") before
they open. That interrupts people constantly while protecting little: a
password typed again proves no more than the first time.

This RFD adds passkeys, a time-based one-time password (TOTP) as a second
factor, and recovery codes. It removes sudo mode, and keeps one narrow, fast
check for the few changes that could take over an account.

Sign-in through an identity provider (RFD 15) is unchanged: that provider is
responsible for its own multi-factor authentication.

== Credentials

An account can hold:

* *Passkeys*: any number of WebAuthn credentials, each with a name the person
  chooses, when it was added, and when it was last used. A passkey may be
  synced (for example through a password manager or platform keychain) or a
  hardware security key.
* *An authenticator app*: one TOTP secret (RFC 6238, 30-second steps, six
  digits).
* *Recovery codes*: ten single-use codes, shown once and stored hashed.
  Generating a new set invalidates the old one.
* *A password*, which becomes optional once the account has a passkey.

An account has multi-factor authentication (MFA) when it holds a passkey or an
authenticator app. Adding the first one generates recovery codes.

Renga uses a pinned, reviewed WebAuthn library for registration and assertion
verification, as RFD 15 does for OpenID Connect. Renga requires user
verification on every passkey ceremony, so a passkey alone is two factors:
the device and its PIN or biometric. It requests no attestation and accepts any
authenticator, storing each credential's ID, public key, signature counter,
transports, and backup flags. The relying party ID is the deployment's
configured host.

== Signing in

The sign-in page offers passkeys first, including browser autofill of saved
passkeys, then email with a password or magic link.

* A passkey signs the person in by itself.
* A password or magic link is the first step for an account with MFA. Renga
  then asks for a passkey, an authenticator code, or a recovery code before it
  creates a session. The half-finished sign-in is bound to the browser, expires
  after five minutes, and grants nothing.
* A password or magic link alone is enough for an account without MFA, as
  today, unless an organization requires MFA (below).

Authenticator codes are rate limited per account, and a code is never accepted
twice: Renga records the last accepted time step. Every failure is recorded for
the account's security log.

Resetting a password by email only replaces the password. It never removes or
bypasses the second step.

== Removing sudo mode

Sudo mode goes away. The settings page opens without asking the person to sign
in again, and no organization administration (members, roles, assignments,
SCIM connections) asks for it.

=== Account re-check

A small set of changes could let someone who has stolen a session keep the
account after the session ends:

* changing the email address or password;
* adding or removing a passkey or the authenticator app, or generating new
  recovery codes;
* linking or unlinking an identity provider (RFD 15).

Each of these asks for one fresh check when the person saves it, in place, not
a separate sign-in page. The check is a passkey assertion or an authenticator
code; an account without MFA enters its password; an account that signs in only
through an OpenID Connect provider re-authenticates there with RFD 15's
`prompt=login` and `max_age` rules. A passing check covers that one change and
any other on this list within the next five minutes, and nothing else.

RFD 15's references to sudo mode mean this re-check.

== Terminal step-up

RFD 13 step-up before opening a terminal becomes an organization opt-in, off by
default. An organization that turns it on asks for a passkey or authenticator
code within the last five minutes, or a fresh password from someone who has
neither. Without it, terminals still require the organization and agent to
enable them, an expiring terminal grant, and recording. The account re-check
never satisfies step-up, and step-up never satisfies the re-check.

== Organization policy

An organization owner may require MFA. Members who sign in with an email
account without MFA are sent to enroll a passkey or authenticator app before
they can open that organization; their other organizations are unaffected.
Sign-in through an RFD 15 identity provider satisfies the requirement, because
that provider enforces its own factors. Turning the requirement on never signs
anyone out; it applies at their next request to the organization.

== Recovery

A person who loses every passkey and their authenticator app signs in with a
recovery code, which counts as the second step and is then spent. Renga prompts
them to add a new factor.

A person with no factors and no codes left cannot recover the account through
Renga's web interface. An operator can remove a user's MFA with a release
command, which records who ran it in the user's security log; organization
owners cannot, because they do not control the person's other organizations.

== Security log and notices

Each account has a security log of sign-ins, failed second steps, and every
credential change, visible in settings. Adding or removing a passkey or the
authenticator app, generating recovery codes, using a recovery code, and
changing the email or password send a notice to the account's email address,
and an email change also notifies the old address.

== Open questions

. *Passwordless accounts.* The proposal lets an account with a passkey remove
  its password entirely, and lets new accounts register with only a passkey.
. *Trusting provider MFA.* The proposal accepts any RFD 15 sign-in as meeting
  an organization's MFA requirement. A stricter rule would check the ID
  token's `amr` claim, which not every provider sends.

== Future work

* Requiring MFA for the whole deployment, not just per organization.
* Checking `amr` from identity providers that send it.
